# 原型需求文档（Figma / .md）→ 开发计划活文档（fw_dev_spec）

> 本文件是 `frontend-workflow` 统一 skill 的第 7 个分支（**3.7 开发计划活文档**）的核心规则正文。命中分支后由 `SKILL.md` 路由 `Read` 本文件执行。
>
> 本分支是 **原型 → OpenSpec PRD（3.2）的可切换替代方案**：面向“需求理解 → 规范产出”上游阶段，把用户提供的 **Figma 原型** 或 **`.md` 格式原型** 统一转化为本地 `.md` 格式的「开发计划活文档」，供下游 ⑧⑨（`frontend-engineering-standards`）实现使用。**本分支默认不写入、不修改任何 OpenSpec（`openspec/`）文件**，与 OpenSpec 路径默认二选一、互不污染；当用户在生成流程中显式开启「OpenSpec 关联模式」（见第九章）后，才按该章规则将活文档单向同步到 OpenSpec 并建立双向关联锚点。
>
> 输入源读取与需求分析**不在此重复定义**，交叉引用 `references/prototype-to-openspec-prd.md` 的第二章 2.2（Figma 获取）/ 2.3（`.md` 读取）/ 2.4（需求分析要素清单）/ 第十章（严禁猜测 / 停止询问 / `⚠️ 待确认` 协议）。活文档的进度状态标记**复用** `references/tapd-plan-template.md` 的 `⬜ / 🔄 / ✅ / ⏭` 约定与「进度总览 + Agent 更新规则 + 中断恢复」模式。

## 何时使用本分支（替代 3.2）

当用户请求以下任一操作时，触发本分支（而非 3.2 OpenSpec）：

- 把 Figma 原型 / `.md` 原型 **转为开发计划活文档** / 需求开发计划 / fw_dev_spec / dev spec
- 明确要求「用活文档方式」而非 OpenSpec 来组织需求规范
- 需要一份**本地可读、可随开发进度实时更新**的需求开发计划（而非 OpenSpec 提案/增量结构）
- 需要在开发过程中，让 Agent 能依据「原需求原型文档」的**关联锚点**快速定位查询需求来源

> 若用户未指定、且需求体量适合 OpenSpec 协作，仍默认走 3.2；本分支是**显式选择**的替代方案。

## 一、工作流总览

```
判定输入源（Figma 或 .md）→ 读取并结构化需求（交叉引用 3.2 的 2.2/2.3/2.4）
   → [Figma 输入] 先转为 .md 原型草稿 → 【人工 Gate·原型审阅】确认无误
   → 存放原需求原型文档到 fw_dev_spec/<需求名-日期>/ 根
   → 确认目录（fw_dev_spec 不存在则询问是否新建；子目录名默认 需求名-日期 或询问）
   → 建议并【询问】组织形式（单文档 vs 多 spec 文档）
   → 【可选 Gate·OpenSpec 关联】询问是否同步初始化 OpenSpec 并建立关联（默认不开启，见第九章）
   → 生成开发计划活文档（specs/ 子目录，五模块统一规范；开启关联模式时嵌入 9.4 同步配置块）
   → 开发中实时更新进度（⬜→🔄→✅），变更记变更日志；开启关联模式时模块②③④⑤变动须先 delta 回写 OpenSpec（见 9.3）
```

| 阶段 | 关键动作 | 产物 / 检查点 |
|------|----------|---------------|
| 1. 输入判定与读取 | Figma（MCP/链接/截图）或 `.md`（路径/粘贴）；结构化需求清单见 3.2 的 2.4 | 结构化需求清单 |
| 2. Figma→.md 原型转换 | 仅 Figma 输入需要：读内容后转为 `.md` 原型草稿 | 【人工 Gate·原型审阅】确认后存放 |
| 3. 原型归档 | 原需求原型文档存 `fw_dev_spec/<需求名-日期>/` 根 | `原需求-原型.md` |
| 4. 目录确认 | `fw_dev_spec/` 不存在则询问新建；子目录名确认 | 目标路径 |
| 5. 组织形式决策 | 按需求大小建议并询问：单文档 / 多 spec 文档 | 用户选定 |
| 5.5 可选 OpenSpec 关联 | 【可选 Gate】询问是否同步初始化 OpenSpec 关联；开启则 init 脚手架 + 双向锚点（见第九章） | 关联模式开关 / openspec 环境就绪 |
| 6. 生成活文档 | 写 `specs/` 下文档，五模块统一规范（关联模式嵌入同步配置块） | 开发计划活文档 |
| 7. 开发随行更新 | 实时更新进度与状态标记，变更追加变更日志 | 进度同步、可追溯 |

## 二、输入源读取与需求分析（交叉引用）

输入源判定、Figma 获取、`.md` 读取、需求分析要素清单、停止并询问与严禁猜测协议，**全部复用** `references/prototype-to-openspec-prd.md`，不在此复制：

- **2.1 输入源判定**：Figma / `.md` / 两者互补 / 都没有则停止询问。
- **2.2 Figma 原型数据获取**：优先 Figma MCP（`get_figma_data` / `download_figma_images`），不可用则回退链接/截图/口述；拿不到关键信息停止询问。
- **2.3 `.md` 格式原型读取与解析映射**：标题层级→模块、表格→字段、有序列表→流程、引用块→约束；停止询问点见 2.3.4。
- **2.4 需求分析要素清单**：页面/模块结构、组件、交互、数据字段、状态、业务流程、边界异常、非功能需求。
- **第十章 边界与不确定处理**：严禁猜测（接口契约/业务规则/字段含义/状态），`⚠️ 待确认` 标记协议。

> 本文件后续步骤在「已取得结构化需求清单」的前提下继续；如需理解提取规则，先 `Read` `references/prototype-to-openspec-prd.md` 对应章节。

## 三、Figma → .md 原型文档转换（仅 Figma 输入）

当用户提供的是 **Figma 原型** 时，必须先将其内容转化为一份 `.md` 格式原型文档，供用户审阅确认后再归档，避免 Agent 基于未确认的设计理解继续下游。

### 步骤 — 转换与审阅 Gate

1. 按第二章 2.2 读取 Figma 内容（布局/页面/组件/交互/字段）。
2. 将内容整理为结构化的 `.md` 原型文档草稿，章节映射遵循 `prototype-to-openspec-prd.md` 2.3.2（标题→模块、表格→字段、有序列表→流程、引用块→约束）。
3. **【人工 Gate · 原型审阅】**：向用户展示 `.md` 原型草稿，请其确认无误；若用户提出修改，按反馈修订后再次确认。
4. 确认通过后，将 `.md` 原型文档存至 `fw_dev_spec/<需求名-日期>/原需求-原型.md`（目录规则见第四章）。

> 若用户提供的是 `.md` 原型，则跳过本步骤，直接按第四章归档（可原样存入，或经轻微规整后存入，规整也需用户知晓）。

## 四、目录结构与命名规范

产物默认落在**当前项目根目录**下的 `./fw_dev_spec/`。按用户确认决策（原型与活文档分层）组织：

```
<项目根>/
└── fw_dev_spec/                          # 开发计划活文档根目录
    └── <需求名>-<YYYY-MM-DD>/            # 单个需求的工作区（子目录）
        ├── 原需求-原型.md                 # 原需求原型文档（Figma 转换后或用户原 .md 规整副本）
        └── specs/                        # 开发计划活文档（活文档主体）
            ├── 开发计划.md                # 单文档模式：五模块合一
            └── <模块A>.md / <模块B>.md    # 多文档模式：按功能模块拆分（均含五模块骨架）
```

### 4.1 根目录 `fw_dev_spec/` 处理

- **已存在**：直接使用，不新建、不改名。
- **不存在**：**询问用户是否新建**（不自动执行 `mkdir`）。用户同意后创建后再写入。

### 4.2 子目录命名

- 默认 `<需求名>-<YYYY-MM-DD>`（如 `订单管理-2026-07-21`）。
- 若默认命名不合适，**直接询问用户**期望的子目录名；写入前确认该路径。
- 同一需求多次迭代时，沿用首次子目录或按日期新建，由用户决定；不自动覆盖既有活文档。

### 4.3 分层存放

- **原需求原型文档**置于子目录**根**（`原需求-原型.md`）。
- **开发计划活文档**置于 `specs/` **子目录**下。

## 五、统一输出规范（活文档五模块）

无论「单文档」还是「多 spec 文档」形式，开发计划活文档均须包含以下**五个统一模块**，确保不同需求/文档格式一致、便于 Agent 理解。

### 模块 ① 当前项目说明

- 项目背景、技术栈（Vue2/3、React、小程序等）、目录约定、运行/构建命令。
- 本活文档范围与关联的原需求原型文档路径（如 `../原需求-原型.md`）。
- 关联 OpenSpec（仅开启「OpenSpec 关联模式」时填写，见第九章）：`openspec/specs/<capability>/spec.md` 相对路径；并在本模块内嵌 9.4 同步配置块（`<!-- openspec-sync -->`），Agent 编辑活文档时**保留此块**。

### 模块 ② 需求功能模块设计

- 按功能域/页面拆分模块，每个模块含：目标、包含功能点、关键交互、数据字段、边界与异常、非功能要求。
- **关联锚点（必填）**：每条需求/功能点须标注与「原需求 `.md` 原型文档」的对应关系，格式：

  ```markdown
  > 来源：原需求-原型.md · 章节「## 订单列表页」/「### 导出报表」
  ```

  便于 Agent 在开发遇疑时快速定位查询原始需求，避免凭记忆臆断。

### 模块 ③ 按步骤划分的开发计划（Plan）

- 将功能模块映射为可执行、可验证的开发步骤（任务），按阶段/顺序组织，任务可勾选：

  ```markdown
  ## 开发计划
  - [ ] P1.1 <任务描述>  （关联模块：订单列表）
  - [ ] P1.2 <任务描述>
  - [ ] P2.1 <任务描述>  （关联模块：导出报表）
  ```

- 每个任务引用对应功能模块（与模块 ② 的锚点呼应），避免空泛动作。

### 模块 ④ 整体进度记录

- 复用 `references/tapd-plan-template.md` 的**状态标记与进度机制**：

  | 标记 | 含义 | 何时标记 |
  |------|------|---------|
  | `⬜` | 待开始 | 计划生成时默认 |
  | `🔄` | 进行中 | 开始执行该步骤/模块时 |
  | `✅` | 已完成 | 步骤/模块执行完毕 |
  | `⏭` | 已跳过 | 不需要处理时（附备注） |

- **进度总览表**（放置在活文档顶部或模块 ④ 开头）：

  ```markdown
  ## 进度总览
  | 模块/步骤 | 状态 | 备注 |
  |-----------|------|------|
  | 订单列表 P1.1 | ⬜ | |
  | 导出报表 P2.1 | ⬜ | |
  ```

- **Agent 更新规则**：开始执行 → `⬜` 换 `🔄`；执行完毕 → `🔄` 换 `✅`；跳过 → `⏭` 并备注；每完成一步同步更新进度总览。
- **中断恢复**：Agent 重新进入时先读进度总览，从第一个 `⬜` 或 `🔄` 处继续，不打断整体进度。

### 模块 ⑤ 变更日志

- 记录需求/计划的所有变更（新增功能、范围调整、锚点修正等），含日期、变更内容、影响范围：

  ```markdown
  ## 变更日志
  | 日期 | 变更内容 | 影响 |
  |------|----------|------|
  | 2026-07-21 | 新增「批量导出」需求 | 模块②新增、P2.1 调整 |
  ```

- 不确定项以 `> ⚠️ 待确认：...` 标记，确认后补全并可在变更日志记录澄清。

## 六、组织形式决策（单文档 vs 多 spec 文档）

生成前**按需求大小给出建议，并询问用户**采用哪种组织形式：

| 情形 | 建议 | 形式 |
|------|------|------|
| 单一模块 / 小型需求 / 功能点少 | 建议**单文档** | `specs/开发计划.md`（五模块合一） |
| 多独立模块 / 中大型需求 / 模块可并行 | 建议**多 spec 文档** | `specs/<模块A>.md`、`specs/<模块B>.md`（每个文档含五模块骨架；模块 ④ 进度总览可各文档独立或集中在 `specs/开发计划.md`） |

- 询问话术示例：“该需求涉及 3 个相对独立的功能模块，建议拆分为多份 spec 文档便于并行与维护；是否采用？（或选择单文档合并）”
- **必须等用户选择后再生成**，不可默认假设。
- 多文档模式下，模块 ② 的「关联锚点」与各文档一一对应，避免跨文档重复定义同一需求。

## 七、与上下游的协作定位

```markdown
[Figma / .md 原型]
      │
      ▼ 3.7 开发计划活文档（本分支，替代 3.2 OpenSpec PRD）
      │   → fw_dev_spec/<需求名-日期>/原需求-原型.md + specs/活文档
      │
      └── 替代 ⑤ PRD，供下游使用：
          ▼ ⑧ 设计桥梁：组件树 / 状态 / 数据流草案   · frontend-engineering-standards
          ▼ ⑨ 生成业务逻辑并绑定静态页面             · frontend-engineering-standards
```

- **与 3.2 OpenSpec 的关系**：默认二选一。本分支默认**不写入、不读取 `openspec/`**，亦不影响其 `specs/changes`；用户选定本分支即意味着用活文档替代 OpenSpec PRD 作为 ⑧⑨ 的输入。**可选增强**：用户在生成流程中显式开启「OpenSpec 关联模式」（见第九章）后，活文档单向同步到 OpenSpec 并建立双向锚点，二者为「关联镜像」而非互斥；未开启则维持互斥。
- **与 3.1 / 3.3 的关系**：同 3.2，下游实现（视觉还原 + 工程规范）仍由对应分支负责；本分支只产出需求与开发计划，不写代码、不做像素级还原。
- **与 3.6 TAPD 缺陷修复的关系**：两者均为独立生命周期分支；缺陷修复的开发计划可参考本分支产出的活文档（如模块 ② 锚点），但各自目录与文档独立。

## 八、通用协作约定（沿用 skill 总原则）

- **生成 → 检查 → 确认 Gate**：原型审阅（第三章）、目录新建（4.1）、组织形式（第六章）均为不可跳过的人工 Gate；到达即暂停等待用户确认。各 Gate 的提问格式统一按 `references/grilling.md` 全局追问协议执行（❓逐题编号 + ➡️每题附推荐答案，可零修改确认）。OpenSpec 关联（第九章 9.1）为**可选** Gate，默认项为「不开启」，不影响默认「二选一」语义，到达即询问但不强制。
- **严禁猜测**：接口契约 / 业务规则 / 字段含义未知时停止询问，以 `⚠️ 待确认` 标记，绝不臆造（协议见 `prototype-to-openspec-prd.md` 第十章）。
- **活文档随行更新**：开发中实时维护模块 ④ 进度与模块 ⑤ 变更日志，确保活文档始终反映当前真实状态，中断可恢复。开启「OpenSpec 关联模式」时，模块 ②③④⑤ 任一变动须先按 9.3 以 delta 回写 OpenSpec 再结束本次任务，并在模块 ⑤ 记录本次同步。

## 九、可选 OpenSpec 关联模式（单向同步）

> 本模式是 3.7 的**可选增强**。默认情况下本分支仍与 OpenSpec「二选一、互不污染」（见第七章）；仅当用户在生成流程的「可选 Gate · OpenSpec 关联」中显式确认，才进入本模式：活文档仍是唯一真相源，OpenSpec 作为结构化镜像，二者通过双向锚点可追溯，活文档后续变更经 delta 回写 OpenSpec。

### 9.1 触发时机（可选 Gate）

在第六章「组织形式决策」确认后、生成活文档前，新增一个**可选**人工 Gate：

```
【可选 Gate · OpenSpec 关联】
- 当前需求：<需求名>
- 说明：是否同步初始化 OpenSpec 并在此活文档与 OpenSpec 间建立双向关联？
        开启后：活文档为真相源，后续变更自动以 delta 回写 OpenSpec（单向）。
        不开启：维持默认「二选一」，本分支不写任何 openspec/ 文件。
- 请确认：[开启关联并初始化 OpenSpec] / [不开启（默认二选一）]
```

- 用户选「不开启」→ 维持默认行为，不写 `openspec/`。
- 用户选「开启」→ 进入 9.2 初始化；本 Gate **不强制**，默认项为「不开启」，避免改变既有二选一语义。

### 9.2 初始化关联（init）

确认开启后，执行以下初始化（Agent 可调用 `scripts/sync-fw-openspec.cjs init` 完成脚手架与锚点注入）：

1. **环境校验**：按 `references/prototype-to-openspec-prd.md` §3 检查 `openspec --version`；
   - 未安装/缺失 → 复用 §3.2 安装引导话术（`npm install -g @fission-ai/openspec@latest`），**停止并请用户确认**后再 `openspec init`，不静默创建。
   - 已就绪但项目无 `openspec/` → 引导 `openspec init` 初始化目录。
2. **确定 capability / change-id**：沿用 `prototype-to-openspec-prd.md` §7.5 kebab-case 约定；capability 表达需求能力域（可用「需求名」转 kebab-case），change-id 用动词短语（如首次快照 `bootstrap-<需求名>` 或 `init-from-fw-dev-spec`）。
3. **脚手架**：创建 `openspec/changes/<change-id>/`（proposal/design/tasks 骨架）与 `openspec/specs/<capability>/spec.md`（空规范占位，待首次 sync 填充）。
4. **注入双向锚点**：
   - 活文档侧：在模块①「当前项目说明」写入「关联 OpenSpec」字段（指向 `openspec/specs/<capability>/spec.md` 相对路径），并嵌入 9.4 同步配置块。
   - OpenSpec 侧：在 `openspec/specs/<capability>/spec.md` 顶部写入 `> 来源：fw_dev_spec/<需求名-日期>/specs/开发计划.md`（多文档模式指向对应模块文档），回指活文档。
5. **写入同步指纹**：计算活文档模块②③④⑤ 文本的哈希，写入配置块的 `lastSyncFingerprint`。

### 9.3 回写规则（sync，单向）

活文档为唯一真相源。当模块②需求功能设计、③开发计划、④进度、⑤变更日志任一发生变动（配置块指纹漂移），须将变更以 `+`/`-` delta 回写 OpenSpec：

- **语义转换由 Agent 负责**：依据 `references/prototype-to-openspec-prd.md` 第四章，将活文档模块②的功能点转为 `### Requirement:`（SHALL）+ `#### Scenario:`（GIVEN/WHEN/THEN），写入 `openspec/specs/<capability>/spec.md`（与 `scripts/sync-fw-openspec.cjs` 的脚手架/校验目标一致）；模块③④⑤的进度/计划/变更可在 `openspec/changes/<change-id>/design.md` / `tasks.md` 中同步记录。
- **delta 规则**：复用 `prototype-to-openspec-prd.md` §4.3 / §6，用 `+`/`-` 表达增删，不整篇重写主 specs；不反向改写活文档。
- **刷新指纹**：回写完成后重新计算并写入 `lastSyncFingerprint`，保持 check 一致。
- Agent 可在每次编辑活文档后调用 `node scripts/sync-fw-openspec.cjs sync <live-doc-path>` 辅助脚手架与校验；脚本不重写 OpenSpec 写作逻辑，仅做文件脚手架、锚点校验与指纹管理。

### 9.4 活文档同步钩子配置块

在活文档模块①内嵌如下 HTML 注释块（由 `scripts/sync-fw-openspec.cjs` 读写，Agent 编辑活文档时**保留此块**）：

```markdown
<!-- openspec-sync -->
openspecSync:
  enabled: true
  openspecPath: ../../../openspec       # 相对活文档所在 specs/ 目录解析（向上 3 级到项目根）
  capability: <capability>
  changeId: <change-id>
  lastSyncFingerprint: <hash>
<!-- /openspec-sync -->
```

**钩子约定（自包含）**：任何后续会话读取到本块且 `enabled: true` 时，即视为已开启关联模式；当模块②③④⑤发生变更（指纹漂移），**必须先执行 sync 回写 OpenSpec 再结束本次任务**；模块⑤变更日志须记录本次同步。

### 9.5 校验（check）

执行 `node scripts/sync-fw-openspec.cjs check <live-doc-path>` 输出结构化结果：

- openspec 环境是否就绪、`openspec/specs/<capability>/spec.md` 是否存在；
- 双向锚点是否完整（活文档模块①关联字段 + OpenSpec spec.md 来源回指）；
- `lastSyncFingerprint` 与当前活文档模块②③④⑤ 哈希是否一致；
- 不一致时列出待同步项（哪些模块变更未回写）。
