# 全局追问协议 grilling（拷问式澄清）

> 定位：frontend-workflow **全局统一的询问协议**——所有需要向用户澄清决策的场景（意图解读、人工 Gate、角色不确定上报、边界不确定处理）一律按本协议执行，替代各自为政的零散问法。
> 来源：整合自 grilling skill 方法论（拷问式追问，relentless interview），按工作流场景工程化（收敛护栏、编排器统一持有）。
> 核心目标：**动手前把决策树走完，消灭"默默假设"**——frontier 清空（无任何未被用户确认的假设）才开始生成/执行。

## 一、何时触发

满足以下任一情境即按本协议组织询问（多问合并不逐条零散发问）：

1. **意图解读**（SKILL.md 2.1）：任务边界、输入物、起止阶段、技术栈任一维度不明确；
2. **人工 Gate**（SKILL.md 2.3）：④⑤a⑦⑦c⑧a⑪⑫ 及各内嵌 Gate（⑤a/⑦b/⑧a/测试用例审阅等）向用户请确认时；
3. **角色不确定上报**：执行 agent 遇"严禁猜测"情形（接口契约未知、业务规则歧义、字段含义不明）需用户裁决时；
4. **边界不确定处理**：各 reference 中标注"停止询问 / ⚠️ 待确认"的场景（如测试范围缺失、项目无测试框架、原型字段歧义）。

**不适用**：用户已明确给出完整决策、纯事实性问题（见第五章，自查解决）、可用合理默认值且用户已授权默认的场景。

## 二、设计树与 Frontier 轮次机制

1. **建模设计树**：把当前任务的待决事项建模为一棵决策树——每个已定决策分叉出其下游决策（如「业务文档方案=fw-dev-spec」分叉出「单文档 or 多文档」「是否关联 OpenSpec」）。
2. **计算 frontier**：每轮只收集**前置条件已落定**的问题（现在就能问、无需猜未听到的答案）；依赖本轮未决问题的问题归入**下一轮**，不提前问。
3. **整轮提出**：把当前 frontier 全部问题**一次性**提出（编号 Q1~Qn，每题带推荐答案），然后**停下等待用户回答**，不边问边做。
4. **重算推进**：用户的回答使部分决策落定，frontier 向外推——重新计算后进入下一轮，直到 frontier 清空。
5. **终止条件**：frontier 清空 = 决策树走完、没有任何东西被默默假设。**用户确认"共识达成/开始执行"之前，不得动手生成或修改任何产物。**

## 三、轮次格式规范

每轮按以下格式输出（强制，所有询问点统一）：

```
❓ Q1 - **<决策标题>**：<问题正文，可含多个选项 A/B/C 及各自后果>

➡️ <推荐答案及理由（一两句）>

---

❓ Q2 - **<决策标题>**：<...>

➡️ <推荐答案及理由>
```

格式要点：
- **逐题编号**（Q1、Q2…），轮与轮之间编号延续（第二轮从 Q(n+1) 起），便于用户引用回答（如"Q1:B，Q2 同意推荐"）；
- **每题必须带 ➡️ 推荐答案**：用户可以零修改回复"全部按推荐"，把决策成本降到最低；
- **决策标题 ≤20 字**，正文先给上下文再给选项，不堆砌无关背景；
- 涉及敏感操作（cross-cutting.md 四）的选项须标注影响范围与可逆性。

## 四、收敛护栏（防止无限追问）

grilling 原方法论为 "relentless"（无上限追问），本工作流加三道护栏防止追问失控：

| 护栏 | 规则 | 超限处理 |
|------|------|----------|
| 轮内规模 | 每轮 **≤4 问**（超出则按对任务的影响排序，低优先级并入"假设清单"） | 挤出的项默认按推荐值执行并显式记录 |
| 同点轮次 | **同一决策点最多追问 2 轮**（用户答复仍不明确时最多澄清一次） | 第 3 次起降级为「剩余假设清单」：把未决项连同推荐值一次性列出，请用户**逐项确认或整体授权默认** |
| 全程轮次 | 意图解读阶段追问 **≤3 轮**（与检查回流上限 3 次的收敛文化对齐） | 触顶即输出假设清单 + "可随时纠正"声明，进入下一环节 |

**假设清单格式**：

```
【剩余假设 · 一次确认】
- 假设1：<内容>（推荐/默认值：<x>）—— 如无异议按此执行
- 假设2：<...>（默认值：<y>）
请回复 [全部按假设执行] 或指出需调整的编号。
```

降级后仍须用户确认（哪怕是整体授权默认），**不得带着未确认假设直接动手**。

## 五、职责分离（事实自查 vs 决策归用户）

- **事实 agent 自查，不问用户**：凡能通过工具探明的事实（项目技术栈、目录结构、package.json 既有依赖、业务文档是否存在于根目录、接口文件现状），一律自行 Read/搜索/派子代理探查后再决策，**禁止拿可自查的事实消耗用户提问额度**；探查中的问题不阻塞 frontier 其他问题。
- **决策必须交用户拍板，不替用户选**：方案取舍（OpenSpec vs fw-dev-spec）、范围增减、Gate 通过与否、涉及不可逆操作的取舍，一律按第三章格式交用户；即使有推荐答案，未经用户确认不得视为已决。
- **多 agent 模式下由编排器统一持有**：执行 agent 的不确定点**上报编排器**（写法见第六章），不得自行向用户发问；编排器把上报项并入 pendingConfirmations（`{id, question, options, recommendation, resolved, source}`，比旧 schema 多 `options`/`recommendation` 两字段），凑满一轮 frontier 后统一按第三章格式问用户。
- **答案回写**：用户确认的决策记入上下文传递（SKILL.md 2.4）与 pendingConfirmations 置位 resolved，后续阶段直接引用，不重复追问。

## 七、与其他章节的关系

- 与 `SKILL.md`：2.1 意图解读与 2.3 人工 Gate 的行为规则由本文件定义，SKILL.md 只保留格式骨架与指针（"不内联规则正文"）。
- 与 `references/cross-cutting.md`：本协议管"怎么问"，cross-cutting 管"什么必须先问"（敏感操作清单四）与硬约束；两者在 Gate 场景叠加生效。
- 与 `references/frontend-engineering-standards.md`（AI 不确定时处理协议）：其"严禁猜测/标记待确认"是**何时必须问**的判定标准，本协议是**怎么问**的执行格式。
- 与 `references/multi-agent-orchestration.md`：编排器统一询问职责（§六）与 pendingConfirmations 机制按本协议第五、六章执行。
- 与 `references/testing.md` / `fw-dev-spec.md` / `tapd-bugfix-workflow.md`：各自的人工 Gate 话术引用本协议格式。
